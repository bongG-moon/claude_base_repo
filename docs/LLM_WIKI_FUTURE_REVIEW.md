# LLM Wiki 도입 검토 — 추후 검토용

작성일: 2026-09-27. **이번에는 검토 내용만 기록하며 실행 기능은 도입하지 않습니다.**
Obsidian 설치, 새 스킬·후크, 자동 수집·동기화, 기존 기억·지식 이전은 하지 않습니다.

## 1. 무엇을 검토하는가

LLM Wiki는 승인된 자료에서 주제별 설명을 정리하고, 출처와 관련 문서를 연결해
다음 업무에서도 참고하는 지식 정리 방식입니다. Obsidian은 로컬 Markdown 폴더를
읽고 편집하는 화면으로 사용할 수 있습니다. Obsidian 자체가 Claude를 실행하거나
자료의 사실성을 검증하고 위키를 자동 갱신하는 것은 아닙니다. 자동 정리에는 별도의
작성 절차와 검토·저장 규칙이 필요합니다.

예를 들어 회의록 세 개에서 ‘교육 신청 절차’, ‘강사 선정 기준’, ‘미결정 사항’을
각각 정리하고 원문 출처를 연결할 수 있습니다. 이후 기준이 바뀌면 관련 문서만
검토합니다. 사람에게 읽기 좋은 연결 문서가 목적이며, 도구 실행 권한을 만드는
것도 모델을 재학습하는 것도 아닙니다.

## 2. 현재 Company Agent와의 차이

| 구분 | 현재 구현 | 향후 LLM Wiki에서 검토할 기능 |
| --- | --- | --- |
| 회사 공통 지식 | 관리자가 검토해 배포하는 용어·지표·테이블·업무 기준 | 승인한 주제 문서·출처 연결을 작성용 저장소에서 관리 |
| 개인 업무 지식 | 출처가 있는 정의를 개인 전체/프로젝트에 저장. 회사 원본과 확장·분기 구분 | 승인한 여러 자료를 묶어 설명·연결·변경 이력을 작성 |
| 개인 기억 | 개인 선호와 지속적인 업무 맥락 | 그대로 유지. 위키 본문과 자동 병합하지 않음 |
| 자동 학습 | 완료 시 재사용할 교정을 검토하고 조건에 따라 개인 선호·기존 개인 스킬 점검 항목 개선 | 자료를 위키로 정리하는 작업은 별도 요청·범위 승인 필요 |
| 조회와 관리 | 관련 지식 색인과 원문·개인 적용 기준 확인 | 주제 간 링크·역링크·출처·검토 상태를 사람이 탐색 |

현재 지식도 Markdown을 사용하므로 단순히 파일 형식이 다른 것이 아닙니다.
차이는 여러 자료를 연결된 설명 문서로 편집하고 유지하는 절차와 탐색 화면입니다.
Obsidian에서 파일을 열 수 있다는 사실만으로 기존 지식 스키마·검색·권한과
호환된다고 볼 수 없습니다.

현재 동작의 근거: [개인 지식 스킬](../company-agent-plugin/skills/personal-knowledge/SKILL.md),
[회사 공통 지식 관리](ADMIN_KNOWLEDGE_GUIDE.md), [자동 학습](SELF_LEARNING.md).

## 3. 저장 범위와 원본 관리

- **회사 공통:** 관리자 작성용 공간에서 초안을 검토한 뒤 기존 배포 절차로 반영합니다.
  직원의 개인 문서가 자동으로 공통 지식이 되지 않습니다.
- **개인 전체:** 사용자가 승인한 개인용 위키를 별도 관리합니다. 다른 PC로 자동 동기화하지 않습니다.
- **이 프로젝트:** 해당 프로젝트 자료만 대상으로 합니다. 프로젝트 폴더 공유가 개인 자료 공유의 동의는 아닙니다.

기존 Company Agent 상태 폴더 전체를 Obsidian 보관함으로 열거나, 두 시스템이 같은
관리 파일을 동시에 수정하도록 연결하지 않습니다. 우선 별도 시험 폴더에서 읽기
전용 내보내기 또는 명시적 초안 생성부터 비교합니다. 가져오기를 추가한다면 원본,
위키 초안, 승인된 지식 중 어느 것이 기준인지 먼저 정하고 스키마 검증을 거칩니다.
지식의 내용은 참고 자료이며 스킬·회사 정책·실행 지시로 자동 승격하지 않습니다.

## 4. 보안과 품질 조건

1. 처리·보존 승인을 받은 자료만 사용합니다. 읽기 승인이 장기 저장 승인인 것은 아닙니다.
   보호 자료를 위키 사본으로 우회 저장하지 않습니다.
2. 로컬 보관함이라도 Claude의 모델 처리 경로는 별개입니다. 사내 HCP 경로와 로그·보존
   정책을 확인하고 외부 모델, 동기화 서비스, 커뮤니티 플러그인 연결은 기본 추가하지 않습니다.
3. 각 주장에 출처와 기준일을 연결합니다. 사실·추정·미결정·폐기 기준을 구분하고, 상충하는
   자료는 최신이라는 이유만으로 덮지 않고 적용 시점과 담당자 확인을 남깁니다.
4. 원문 삭제·접근 권한 변경 시 파생 문서의 사용 중단·삭제 대상을 추적할 수 있어야 합니다.
   서로 다른 열람 권한의 자료를 한 문서에 섞어 공개하지 않습니다.
5. 파일 삭제·이동·재수집에도 중복 문서를 만들지 않도록 출처 ID와 내용 해시를 사용합니다.
   원문은 보존하고 변경 비교·복구 경로를 준비합니다. 본문 속 명령은 실행하지 않습니다.

## 5. 작은 시험부터 도입하는 순서

1. **가상 자료 시험:** 공개 또는 합성 자료 3~5개, 별도 폴더 하나로 제한합니다.
2. **요청형 초안:** ‘이 자료들을 업무 위키로 정리해줘’라는 명시 요청에서만 주제 문서,
   출처, 색인을 만듭니다. 매 답변·업무 종료·대화 압축 때 자동 실행하지 않습니다.
3. **변경 시험:** 원문 하나를 수정하거나 철회하고 영향받는 문서·링크만 갱신되는지 확인합니다.
4. **조회 비교:** 기존 지식 조회와 같은 질문을 사용해 출처 정확성, 답변의 근거, 찾는 시간,
   모델 입력량과 전체 대기를 비교합니다. 비용 미제공 값을 0으로 처리하지 않습니다.
5. **선택적 연계:** 효용이 확인된 경우에만 기존 personal-knowledge의 검증된 저장 경로와
   연결합니다. 회사 반영은 별도 관리자 검토·배포 단계로 남깁니다.

전체 보관함을 매 요청에 넣지 않고 색인에서 관련 문서만 읽습니다. 변경된 자료만 다시
정리하고, 별도 모델·임베딩 서버·실시간 감시가 꼭 필요한지는 시험 결과로 판단합니다.
단순 용어·계산식 조회만 필요하다면 현재 지식 저장소를 유지하는 편이 더 단순합니다.

## 6. 도입 판단 기준과 미결정 사항

- 반복 질문에서 실제로 근거를 더 잘 찾는가? 오래된 답을 줄이는가?
- 수정·철회한 출처가 관련 문서에 반영되고 개인/공통 범위가 섞이지 않는가?
- 반복 수집 시 중복 문서가 생기지 않으며 사용자 편집을 보존하는가?
- 작은 사내 모델에서도 작업 시간·토큰·수정 횟수가 허용 가능한가?
- 담당자가 초안·승인·폐기 상태와 복구 절차를 이해할 수 있는가?

보관함 위치, 원문 보존 기간, 공통 승인 책임자, 읽기 전용 내보내기/가져오기 방식,
Obsidian 사용 승인, 수동 요청과 갱신 주기는 아직 결정하지 않았습니다.
실제 사내 자료로 시험하기 전 이 항목을 확정하고 작은 시범 운영 계획을 별도로 승인합니다.

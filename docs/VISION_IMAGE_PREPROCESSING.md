# 이미지 전달 보완과 다음 개선 계획

확인일: 2026-10-14. 현재 변경은 소스에 반영한 내용이며, 운영 HCP 모델의 인식 품질 검증이나 새 Release 게시를 뜻하지 않습니다.

## 1. Desktop 설명에서 확인되는 것과 확인되지 않는 것

- **Claude Code의 Read도 이미 이미지 크기를 줄이고 재압축합니다.** 공식 문서는 축소 후에도 500KB를 넘으면 같은 픽셀 크기에서 JPEG 품질을 낮춘다고 설명합니다. 따라서 Desktop에만 있는 기능을 CLI에 처음 추가한다는 설명은 맞지 않습니다. [Read 공식 문서](https://code.claude.com/docs/en/tools-reference#read-tool-behavior)
- Desktop에서 받은 “플랫폼이 자동 축소한다”는 답변은 모델의 설명입니다. 공개된 업로드 안내만으로 Desktop의 정확한 변환 알고리즘·설정값·실제 요청 바이트가 CLI와 같다고 확인할 수 없습니다. [Claude 업로드 안내](https://support.claude.com/en/articles/8241126-upload-files-to-claude)
- 이미지 바이트를 줄이면 전송량이 줄 수 있고, 픽셀 수를 줄이면 비전 처리량도 줄 수 있습니다. **같은 픽셀 크기의 압축만으로 토큰이 같은 비율로 줄지는 않습니다.** 이미지가 이미지 블록으로 전달되는지와 모델·서버의 처리 방식도 중요합니다. Claude의 수치를 HCP의 확정 한도로 사용하지 않습니다. [Vision 공식 문서](https://platform.claude.com/docs/en/build-with-claude/vision)
- 이전 로그의 1384×752 이미지는 아래 픽셀 기준보다 작습니다. 그 파일의 실패를 해상도 하나로 설명하거나 “모델은 정상, 크기만 문제”라고 확정할 수 없습니다. base64 글자 수나 모델 자기 보고도 원인 확정 근거가 아닙니다.

## 2. 이번에 적용한 범위

사용자가 선택한 이미지 전용 작업자 또는 HCP 백업 작업자가 PNG·JPEG를 `Read`로 읽은 **성공 결과**만 대상으로 합니다. 모델 선택·변경은 [별도 기록](VISION_MODEL_SELECTION.md)을 참고합니다.

1. 기존 Claude 권한 확인과 Read 실행을 그대로 거칩니다. 실행 전에 원본을 열거나 다른 파일로 경로를 바꾸지 않습니다.
2. 네이티브 Read 결과의 이미지 구조가 맞는지 확인합니다. 문자열 base64·알 수 없는 도구 결과를 임의로 이미지라고 해석하지 않습니다.
3. 이미 적절한 결과는 그대로 둡니다. 보정이 필요할 때만 결과에 들어 있는 바이트를 메모리에서 처리합니다.
4. 큰 이미지에만 종횡비를 유지한 축소 또는 압축을 시도합니다. 잘라내기·늘리기·자동 OCR·재귀 재시도는 하지 않습니다.
5. 정상 보정된 결과만 `updatedToolOutput`으로 반환합니다. 원본 크기 정보와 다른 결과 필드는 보존하고, 이미지 바이트·형식·표시 크기만 바꿉니다.

| 항목 | 현재 기준 |
| --- | --- |
| 긴 변 | 최대 1568px |
| 총 픽셀 | 최대 1,150,000 |
| 결과 이미지 바이트 | 최대 512,000바이트, base64 변환 전 |
| JPEG 압축 | 품질 90, 필요할 때 80까지만; 바이트 때문에 추가로 계속 작게 만들지 않음 |
| 투명 이미지 | PNG 투명도 유지, 검은 배경의 JPEG로 바꾸지 않음 |
| 자원 제한 | 입력 8MiB·20MP 이내만 보정 시도 |
| 회전·애니메이션 | 별도 회전 정보나 여러 프레임이 있으면 무변경 |
| 제외 | 직접 첨부, PDF, GIF/WebP, MCP 캡처, 일반 텍스트 읽기 |

이 값들은 사내 모델의 확정 제약이 아니라 보수적인 호환 보정 기준입니다. 작은 글씨 판독보다 크기 축소를 우선하지 않으며, 한도 안에서 보정할 수 없는 결과는 **원래 Read 결과를 유지**합니다. 잘못된 형식·코덱 오류도 새 도구 오류나 반복 시도를 만들지 않습니다. 그러므로 모든 입력이 위 한도 이하가 된다는 강제 제한 장치는 아닙니다.

**후크를 실행하는 Python에 이미 Pillow가 있을 때만** 같은 프로세스에서 추가 보정합니다. 없으면 CLI 자체의 Read 결과를 그대로 사용합니다. 다른 Python을 찾아보거나 매번 설치 여부를 묻지 않습니다. 자동 패키지 설치·외부 전송·보조 프로세스 호출은 없습니다. 일반 텍스트 작업에는 코덱을 추가하지 않고, 기존 후크 등록 수도 늘리지 않습니다.

Windows 기본 이미지 기능으로 대체하는 방법도 시험했지만 프로세스 시작을 포함해 약 3.1~4.2초가 걸렸습니다. 기존 후크의 5초 제한과 사용성을 고려해 **최종 구현에서 제외**했습니다. Pillow 없는 환경에 반드시 추가 보정이 필요하다면 담당자가 승인된 런타임 패키지 구성에 반영할지 별도로 결정해야 합니다. 이것을 기존 Read 사용의 선행 조건으로 만들지는 않습니다.

Claude Code **2.1.296**에 포함된 Read 출력 스키마와 네이티브 도구 결과 교체 코드를 확인했습니다. 운영 CLI가 `updatedToolOutput`을 지원하는지는 도입 시 확인해야 합니다. 구버전에서 동일하게 동작한다고 가정하지 않습니다. [PostToolUse 공식 계약](https://code.claude.com/docs/en/hooks#posttooluse-decision-control)

### 보호 범위와 한계

- 원본 파일·사용자 설정·인증값을 읽거나 수정하지 않으며, 보정용 디스크 사본·캐시·학습 데이터를 만들지 않습니다. 메인 모델과 기존 승인은 그대로입니다.
- 일반 작업에 시험 요청, 모델 호출, 추가 후크를 넣지 않습니다. 실제 이미지 변환에는 로컬 CPU 시간이 들며 토큰 절감률은 HCP 측정 전에는 주장하지 않습니다.
- PostToolUse는 이미 실행된 결과를 바꿉니다. Claude가 후크 이전에 기록한 원래 이미지나 다른 로그까지 삭제하는 개인정보 정리 기능이 아닙니다.
- 같은 Read 결과를 다른 후크도 수정한다면 마지막 결과가 적용될 수 있습니다. 이번 후크는 변경 없는 결과를 덮어쓰지 않지만, 보안 마스킹 후크와 동시에 쓰는 경우 담당자가 실행 순서·결과를 확인해야 합니다.
- 이미지 입력 형식 누락, 텍스트로 된 base64 전달, 잘못된 모델 연결, 서버 비전 처리 미지원은 해상도 보정만으로 해결할 수 없습니다.

## 3. 다른 내부 처리 방식에서 참고할 항목

| 항목 | 판단 | 적용 계획 |
| --- | --- | --- |
| 작은 이미지 무변경, 큰 이미지 제한 보정 | 이번 적용 | 원본을 건드리지 않고 승인 후 결과만 처리. 상시 모델 시험 없음 |
| 이미지 전용 문맥과 텍스트 반환 | 이미 적용 | 새 비전 작업자가 필요한 2~3장만 관찰. 메인 대화에 이미지·전체 이력을 반복 복사하지 않음 |
| 이미지 블록과 도구 결과의 정확한 전달 | 최우선 운영 확인 | 기존 별도 A/B/C 키트로 일반 이미지·도구 결과 이미지·실제 Read 비교. 회사 게이트웨이의 변환 뒤 이미지 필드를 담당자가 확인; 인증값·원본 업무 자료는 진단 로그에 남기지 않음 |
| 판독이 필요한 영역만 확대 | 다음 후보 | 사용자가 작은 글자 영역을 지정한 경우에만 별도 영역 읽기. 자동 다중 타일·여러 번 재판독은 기본에서 제외. 좌표·확인 범위와 원본을 명확히 구분 |
| 화면 캡처의 크기 조절 | 이번 제외 | 화면 조작 좌표가 달라질 수 있으므로 캡처 도구가 공식적으로 제공하는 크기 옵션과 좌표 변환 계약부터 확인 |
| 긴 텍스트·표·메일 결과의 필요한 범위만 읽기 | 기존 기능 유지·병목 때 보완 | 각 도구의 범위·목록 우선 읽기를 활용. 결과를 무조건 잘라 완전한 결과처럼 보고하지 않음. 같은 업무의 총시간·총토큰으로 비교 |
| 파일 재사용·서버 캐시 | 추후 검토 | 회사 API 지원, 보존 위치·기간·접근 권한을 확인한 뒤 명시적으로 도입. 외부 Files API나 영구 이미지 캐시는 기본으로 추가하지 않음 |
| 모델 재시도·OCR 대체 | 후속 요청으로 제한적 백업 적용 | 실제 모델 호출 불가에만 HCP 백업 1회. 파일·권한·판독 실패 재시도와 OCR 대체는 하지 않음 |

## 4. 운영 비교 방법

기존 [비전 입력 비교 키트](../standalone-guides/vision-input-check/README.md)는 그대로 별도 실행합니다. 작은 정답 이미지가 A/B/C에서 다른 결과를 내면 크기 보정보다 전달 형식부터 조사합니다. 큰 이미지 보정은 별도의 큰 가상 자료로 비교하고, 작은 글씨·숫자 누락도 함께 채점합니다. 모델의 “잘 읽었다”는 설명을 성공 기준으로 사용하지 않습니다.

평소 업무에는 시험을 넣지 않습니다. 회사 모델의 인식 품질, 운영 CLI 버전, 게이트웨이의 이미지 전달과 실제 토큰·지연 효과는 회사 테스트 결과가 있어야 확정할 수 있습니다.

## 5. 이번 로컬 검증 결과

- 비전 인계·입력 비교 키트·Read 빠른 경로·설치·런타임·이미지 처리 회귀 검사 **160개 통과**. 최종 보정 코드의 집중 검사와 검토 지침 검사는 별도로 **37개 통과**했습니다. 이 수치는 서로 겹치므로 합산하지 않습니다.
- 이미지 처리 전용 검사 30개에는 작은 이미지 무변경, PNG/JPEG 크기·비율·투명도, 손상·잘못된 MIME·APNG·EXIF, Pillow 미설치, 승인 후 전용 작업자 범위, 설치 범위 밖 무변경과 추가 프로세스·네트워크 없음이 포함됩니다.
- 기존 PPT 이미지 검토 지침 테스트 3건은 이미 배포된 문서의 제목·문구·비전 인계 추가 전 분량 기준과 맞지 않았습니다. 실제 지침은 더 늘리지 않고 현재 문서 계약으로 테스트를 갱신했으며, 참고 자료와 최종 결과의 검토 범위를 구분하는 검사도 추가했습니다.
- Claude Code 2.1.296을 빈 설정 폴더와 localhost 가상 API에 연결해, Read의 합성 이미지가 PostToolUse 교체 후 다음 요청의 **이미지 블록**에 담기는 것을 확인했습니다. 원본 불변, 정확한 파일 Read만 허용, 실제 모델·외부 인증 사용 없음. 가상 서버의 토큰·비용 값은 실제 성능 근거가 아닙니다.
- 로컬 합성 2400×1600 PNG → 1313×875 보정은 5회 측정에서 약 **49~54ms**였습니다. 작은 이미지 10,000회 무변경 검사는 평균 약 **0.0006ms/회**였습니다. Python 내 함수 처리만 잰 수치이며, 후크 기동·CLI 전체시간·운영 모델 응답시간은 포함하지 않습니다.
- 통합 HTML 안내서를 재생성하고 Markdown 원본·설치용 안내서 사본의 일치 검사를 통과했습니다. 회사 자료나 HCP 모델은 사용하지 않았습니다.

담당자 재실행: 저장소 루트에서 승인된 Python에 `PYTHONPATH=tests;company-agent-plugin/scripts`를 적용하고 `python -X utf8 -m unittest test_vision_routing test_vision_handoff test_vision_input_check test_vision_image_preprocessing test_read_hook test_read_hook_install test_image_review_efficiency test_native_runtime`를 실행합니다. 이미지 변환 테스트에는 Pillow가 필요하며 없으면 해당 검사는 건너뜁니다. 이것은 개발 검증 명령이지 사용자의 평소 업무 단계가 아닙니다.

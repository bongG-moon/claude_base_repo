# 대표 디자인 확인과 승인 후 제작

1. 전체 장수에 맞는 구성과 전체 job JSON을 준비한다. 모든 수치·표·차트·facts,
   선택한 designPreset 또는 분석한 presentationTheme/글꼴을 이 job에 넣는다.
   사용자 자료에 없는 연도·증가 원인·목표 상향 제안을 사실처럼 추가하지 않는다.
2. 설치된 cliCommand로 아래를 실행한다. 기존 파일을 덮어쓰지 않는다.
   `business ppt-design-preview --spec "전체-job.json" --output "새-대표디자인.pptx" --state-root "<stateRoot>"`
   reference/saved 방식은 `--template "확인한-양식.pptx"`도 전달한다.
   이 명령은 전체 자료로 계산을 확인한 뒤 첫 1~2장만 실제 PPT로 만든다.
   표지만으로 색감·본문 배치를 판단하지 않도록 두 번째 장을 대표 본문으로 준비한다.
3. 반환된 previews 이미지들을 실제로 읽고 전체 구성과 함께 사용자에게 보여준다.
   실제 PPT에서 출력한 이미지라는 점과 대표 장만 만들었다는 점을 구분한다.
   이미지 출력이 불가능하면 이유를 짧게 설명하고 대표 PPT 링크를 제공한다.
   사용자가 그 파일을 직접 확인할 수는 있지만, 글로 설명만 하고 미리보기를
   보여줬다고 주장하지 않는다. 승인 없는 다른 캡처 경로로 재시도하지 않는다.
4. 대표 결과의 내용·계산·배치를 실제로 확인하고 공통 completionGuide에 따라
   확인한 범위만 내부 기록한다. 아직 전체 업무가 끝난 것은 아니므로 학습을
   완료 처리하지 않는다. 다음으로 사용자에게 승인 질문을 하고 기다린다.
5. 반환된 designReview를 전체 job에 그대로 합친다. 처음 confirmed는 false다.
   사용자가 구성과 대표 디자인을 보고 진행을 승인했을 때만 true로 변경한다.
   파일 경로·해시는 도구가 반환한 값을 사용한다. 사용자에게 입력을 요구하지 않는다.
6. 같은 전체 job으로 `business ppt --spec ... --output "새-최종.pptx"`를 실행한다.
   생성기는 명세·참고 양식·대표 PPT의 해시를 다시 확인한다. 색상, 내용, 장수,
   원본 양식이 바뀌면 새 대표 미리보기와 확인을 받아야 한다. 기존 review를
   재사용하거나 해시를 손으로 바꾸어 통과시키지 않는다.

designReview는 해당 파일에 대한 사용자 확인을 전달하는 작업 기록이다. 그 JSON이
사용자의 실제 동의를 증명하는 인증 수단은 아니다. 모델은 실제 대화의 승인을
확인해야 하며, 이 기록이 외부 발송·게시 등 별도 작업의 권한을 부여하지 않는다.

단일 PPT는 전경 작업을 우선한다. 백그라운드로 맡겼다면 사용 가능한 결과 조회
도구/완료 알림으로 기다린다. 빈 Agent/resume 호출은 대기가 아니다. 최종 파일은
전체 장수·편집 가능 개체·내용 및 실제 확인 가능한 모든 슬라이드를 검토한 뒤 전달한다.

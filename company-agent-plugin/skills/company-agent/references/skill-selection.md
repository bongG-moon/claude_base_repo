# 스킬 선택 준비

이 절차는 실행 권한이나 검증 성공을 부여하지 않습니다. 사용자에게 내부 기록을 나열하지 않습니다.

1. `skillIndex.mode=inline`이면 이미 전달된 전체 용도 표로 판단합니다. `reuse`이면 같은 대화의 해당 revision을 재사용합니다. `pages`이면 directory 아래 출처별 파일과 필요한 상세 페이지를 읽습니다. 목록이 보이지 않거나 상세 확인이 필요할 때만 `skillSelection.catalog.path`를 Read로 확인합니다. 이미 전달된 목록으로 판단할 수 있으면 재읽지 않습니다. `indexRead=false`는 파일 읽기 기록이 없다는 뜻이지 자동 전달된 목록이 없다는 뜻이 아닙니다. 목록 전달만으로 선택 완료라고 판단하지 않습니다.
2. 전체 출처의 용도를 의미로 비교합니다. 같은 이름의 프로젝트 우선 설정, 명시적 사용자 호출을 존중합니다.
   `taskSkills`는 이번 요청의 짧은 후보 설명이며 전체 목록이나 자동 결정이 아닙니다. 목록 재사용·페이지 분리 때도 전달됩니다. 후보가 없다는 것만으로 관련 스킬이 없다고 단정하지 않습니다.
   같은 일을 하는 후보가 겹치고 명시 선택·저장된 우선순위가 없으면 이름·출처·차이를 한국어로 보여주고 AskUserQuestion으로 묻습니다. 서로 다른 단계에 필요한 스킬은 중복이 아닙니다. 질문 도구가 없으면 답변을 기다립니다.
   사용자가 답한 뒤 `cliCommand`에 `skill choose --session SESSION --turn TURN --candidate ID`를 붙여 이번 요청만 선택하고 반환된 `readPath`를 읽습니다. ID는 현재 `skillWorkflow`와 후보에서 가져옵니다. 원본·우선 설정을 바꾸거나 본문 읽기를 위조하지 않습니다. 기본/프로젝트 저장은 별도 요청 때만 합니다.
3. `skillExecution.mode=load`이면 목록에서 찾은 후보입니다. 요청에 맞으면 지정된 Skill/Read로 본문을 불러옵니다. 후보가 맞지 않으면 전체 목록의 용도를 비교합니다. `reuse`는 성공한 Read/Skill 기록과 현재 파일 해시가 일치할 때만 제공됩니다. 현재 대화의 본문을 사용하고, 보이지 않을 때만 `skillExecution.path`를 읽습니다. 다른 세션 스킬도 같은 역할이면 기존 선택·우선순위를 확인하고 모호할 때 사용자에게 묻습니다.
   등록된 고유 호출명은 Skill 도구로 불러옵니다. 개인 파일, 동일 호출명 충돌, 정확한 파일을 지정하는 우선 설정은 표의 `roots[root]/file`을 Read로 읽습니다. `load`는 실제 호스트의 등록/권한 보장이 아닙니다. Unknown skill이면 정확한 파일로 확인할 수 있지만 실제 권한 거절을 우회하지 않습니다. 성공한 Read 또는 식별 가능한 Skill 호출만 `lastBodyLoad`를 기록합니다. Hook이 후보나 본문을 전달했다는 과거 기록은 선택/로드 증거로 재사용하지 않습니다.
   본문을 목록보다 먼저 읽었어도 그 읽기 기록은 보존됩니다. 목록을 나중에 확인했다는 이유만으로 본문을 다시 읽지 않습니다.
4. 같은 목록 버전에서 이미 읽은 본문이 현재 요청에도 맞으면 그대로 재사용합니다. `skill route`는 선택적 진단 명령이지 필수 단계가 아닙니다. 실행 명령 앞에 결합하지 않습니다. 선택·본문 로드·필요한 사용자 질문을 끝낸 다음 위임합니다. 작업자에게 정확한 선택 파일을 전달하고, 작업자도 자기 대화에서 그 본문을 읽습니다. 부모의 읽기 기록으로 작업자의 로드를 대신하지 않습니다.
5. 관련 스킬이 없으면 일반 작업을 진행합니다. `review`는 키워드 후보가 없더라도 전체 목록을 비교하라는 뜻입니다. 목록을 읽고도 맞는 스킬이 없으면 별도 기록 명령 없이 실행합니다. `general`은 확인된 로컬 목록에 자동 사용 가능한 스킬이 없을 때만 제공됩니다. 세션에 별도 제공된 기본/원격 스킬도 고려합니다. 무관한 스킬을 강제하거나 없는 이름을 만들어 호출하지 않습니다. 목록 조회 실패는 스킬 부재가 아니므로 `inspect`에서는 정확한 목록/경로를 확인합니다.

company-agent, karpathy-guidelines, self-learning 등 공통 조율·보완 지침을 읽는 것만으로 실제 업무 스킬을 선택한 것으로 처리하지 않습니다. 이 지침 자체가 요청의 목적이면 이미 읽은 해당 이름을 명시적으로 선택할 수 있습니다.

단순 위치·폴더 조회(`pwd`, `ls`, `Get-ChildItem` 등)는 준비 차단도 확인 횟수 소모도 하지 않습니다. 읽기 스크립트 실행·출력 파일 리다이렉트가 섞인 명령은 이 예외가 아닙니다. 관련 후보를 확정하지 못한 `review`/`select`/`choose`/`inspect`에서는 짧은 내부 안내만 요청·목록 버전당 한 번 전달하며 Bash/Write를 막거나 무관한 스킬을 강제하지 않습니다. 겹치는 역할의 사용자 선택 지침은 유지합니다.

실제 사용 가능한 단일 `load` 후보의 본문을 건너뛴 업무 실행만 `[스킬 확인]`으로 한 번 교정합니다. 이때 원래 도구는 실행되지 않았습니다. 요청에 맞는 본문을 로드하고 계속합니다. 후보가 맞지 않으면 제공된 목록과 용도를 다시 비교하고 관련 스킬이 없을 때 일반 실행합니다. 파일 권한·샌드박스 오류로 오해해 승인이나 재설치를 요구하지 않습니다. 반복 차단하거나 읽지 않은 본문을 읽었다고 기록하지 않습니다. 실제 권한 거절·보호 제한은 별개로 준수하며 Stop 검증 실패를 추가하지 않습니다.

사용자의 다음 답변에서 `selected`가 비어 있어도 이전 본문을 잊었다는 뜻은 아닙니다. 새 요청에 맞는지 판단하라는 뜻이며, 선택 기록을 채우기 위한 명령을 실행할 필요는 없습니다. “company 스킬로 해당 파일 읽어줘” 같은 짧은 이어서 요청은 직전 업무의 한정된 분야·행동 태그만 참고합니다. 새 분야나 다른 행동이면 이전 업무를 강제로 이어가지 않습니다. 원문 질문·파일 이름을 이 목적으로 저장하지 않습니다.

Read/Glob/Grep/선택 질문/스킬 목록 확인은 막지 않습니다. CLI 선택 기록에도 원래 Claude 권한 규칙은 적용됩니다. 승인이 필요한 환경에서는 선택을 위해 권한을 넓히지 말고 필요한 SKILL.md를 다시 Read하는 방식으로 준비할 수 있습니다.

스킬·선택 설정이 바뀌면 다음 사용자 요청에서 목록이 갱신됩니다. 같은 대화에서 바뀌지 않은 본문은 재사용하지만 변경·삭제된 스킬은 현재 파일처럼 재사용하지 않습니다. 새 세션·재개·컴팩트 이후에는 목록을 다시 전달하고 이전 본문 읽기 기록을 재사용하지 않습니다. 출처별 페이지는 내용 일부를 숨긴 최종 후보 목록이 아니므로, 확인하지 않은 페이지가 있는데 관련 스킬이 없다고 단정하지 않습니다.

이 확인은 지원되는 도구 경로에서 관찰된 읽기 기록을 참고합니다. 모델이 지침을 실제 적용했거나 요청의 의미를 정확히 이해했다는 보증, 다른 플러그인·외부 작업자의 완전한 통제, 보안 샌드박스가 아닙니다.

진단: 세션 JSON의 `hookDiagnostics`에는 시작/질문 Hook의 최신 상태·소요 시간·목록 버전·후보 이름만 저장합니다. `output-produced`는 Hook이 출력을 만들었다는 뜻이며 호스트 수신/모델 적용 증거가 아닙니다. `started`만 남으면 완료 기록이 없어 종료/시간초과 등을 조사해야 합니다. `skillWorkflow.lastBodyLoad`는 성공한 Read/Skill에서 확인한 이름·해시·도구입니다. 원문 질문·문서 내용·예외 메시지는 이 진단에 저장하지 않습니다. 정상 진단을 사용자에게 중계하지 않습니다.
`reviewCheckpoint.status`는 `advised`(안내만 전달, 차단 없음), `redirected`(실제 load 후보 누락 교정), `catalog-read`/`skill-loaded`(실제 읽기 관찰), `unconfirmed-limit-reached`(읽기 없이 재시도, 추가 차단 없음)를 구분합니다. 로컬 목록 밖의 호스트 스킬 성공은 `native-skill-outside-catalog`이며 이를 로컬 본문 해시/다음 요청의 재사용 증거로 만들지 않습니다.

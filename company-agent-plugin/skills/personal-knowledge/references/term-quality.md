# Business terminology quality

Use inside Personal Knowledge authoring, not on every knowledge lookup.

- Search the effective corporate base and active overlays before proposing a term.
  Record a concise definition, useful aliases, scope, and known distinctions in
  the existing Markdown body/spec fields. For tables or metrics include only
  confirmed grain, units, date basis, joins and exclusions; mark unknowns plainly.
- Compare a new definition with existing meanings. Ask one material clarification
  if a conflict changes the answer; otherwise use the narrower task interpretation
  without inventing a permanent standard. Proposed edge cases are hypothetical,
  never source evidence or new business facts.
- Save an explicit durable correction through the parent knowledge upsert flow.
  Inferred patterns follow its confirmation rule; do not silently save them or
  start an additional learning review. Interaction preferences remain Personal
  Memory and ordinary unfinished-work preference feedback remains staged.
- Reuse extend/fork/personal-new and the existing reconciliation rules. Keep a
  personal fork visibly distinct from the corporate definition. No direct edits
  to the corporate base, plugin, CLAUDE.md, or an existing project glossary merely
  because upstream uses CONTEXT.md. User/project state scopes remain separate.
- Keep definitions separate from implementation plans. Record a short decision
  rationale only for a real, consequential trade-off; do not create an ADR for
  every chat. Preserve references to approved source documents, not raw mail,
  protected content, secrets, or data rows. No new knowledge database is needed.

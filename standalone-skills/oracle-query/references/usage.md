# 관리와 예외

기본 조회에는 이 문서가 필요하지 않습니다. 요청받은 설정, 정리, 승인 대기 또는 오류에 해당하는 항목만 확인합니다. SQL 등록은 [등록 안내](interaction.md), 후처리는 [Python 후속 처리](workflows.md)에 있습니다.

## 처음 설정하거나 인증값이 없을 때

기존 연결을 사용하고, 인증값이 없거나 연결 추가/수정을 요청받았을 때만 `profiles setup`을 실행합니다. 기존 항목 수정은 `profiles setup --profile <ID>`입니다. DB 표시 이름과 조회 조건은 채팅으로 확인해도 되지만 인증값은 로컬 입력창에서 받습니다.

“인증정보는 채팅에 보내지 말고, 지금 여는 내 PC 입력창에 직접 입력해 주세요.”라고 알리고 설정 명령을 실제 실행합니다. 창이 열렸다는 근거 없이 열었다고 말하지 않습니다. 창 열기 실패나 취소이면 상태를 알리고 멈춥니다. 채팅 입력으로 우회하거나 자동으로 다시 열지 않습니다. 이미 채팅에 적힌 비밀값도 재인용하거나 명령 인자, 로그, 등록 명세에 옮기지 않습니다. 설정 저장과 접속 성공은 별개입니다.

## 필요한 명령만 선택

아래는 `python -X utf8 -B "<현재 스킬 절대경로>/scripts/query.py"` 뒤의 인자입니다. 사용자에게 명령 작성을 맡기지 않으며 설치 폴더로 cd하거나 PC 전체에서 설정을 찾지 않습니다.

| 목적 | 인자 |
|---|---|
| 저장 목록이 필요함 | `queries list` |
| 조건 정의를 모름 | `queries show --id <번호>` |
| 관리 화면 요청 | `manage` |
| 저장 결과의 상태 확인 | `result --id <결과 ID>` |
| CSV 전달만 재시도 | `export-csv --id <결과 ID> --output <새 CSV 경로>` |

목록과 상세 조회는 이미 알려진 값을 다시 얻으려고 실행하지 않습니다. 관리 화면은 사용자가 요청한 때만 엽니다. 명확한 일반 조회는 SKILL.md의 `execute` 한 번으로 계획 검사와 실행, CSV 전달까지 처리합니다. 별도 계획만 요청했을 때는 `plan --id <번호> --param 이름=값`을 사용합니다.

## 새 업무의 이전 결과 정리

새 조회 업무에서 한 번 실행하는 `start`는 메타정보만 읽으며 접속하거나 결과 행을 읽지 않습니다. 24시간이 지난 결과 중 최대 10개 정리 후보를 준비합니다. 후보가 있을 때만 `cleanup.count`와 `cleanup.totalBytes`로 실제 삭제 범위를 보여 주고 한 번 선택받습니다. 허락했다면 `results cleanup --plan <cleanup.planId> --confirm`을 실행합니다.

정리 여부를 묻기 전에는 결과 본문을 읽지 않고 파일 정보와 기존 확인 기록만 준비합니다. 삭제를 허락받은 뒤에만 파일 전체의 SHA를 검증하며 바뀐 파일은 보존합니다. 원본 SHA 기록이 없는 구형 결과는 자동 정리 후보에서 제외합니다.

후보가 없거나 보존을 선택했다면 바로 조회합니다. 이미 정리 여부를 확인한 같은 업무에서는 조건이 달라져도 다시 `start`하지 않습니다. 계획에 없는 파일, 이후 바뀐 결과, 후속 분석에 필요한 결과, 연결과 쿼리 원본은 지우지 않습니다. 별도 정리 요청은 `results list --limit 20`과 `results cleanup-plan --id <결과 ID>`로 지정한 대상만 준비합니다. 준비와 실제 삭제는 구분합니다.

## 실행하지 않고 승인을 기다리는 경우

일반 조회는 승인 없이 실행합니다. 최근 7일 안에 같은 SQL, 연결, 인증 설정, 조건과 한도로 작은 전체 결과가 확인됐으면 범위 확인을 재사용하며 데이터는 새로 조회합니다. 사용자 함수나 실제 조건 없는 조인은 해당 위험의 명시적 승인 뒤 작은 전체 결과가 완료된 경우에만 같은 범위의 재승인을 생략합니다. 등록 때 최대 10행을 읽은 시험은 전체 규모 근거가 아닙니다. 조건이나 설정 변경, 부분 결과, 오류, 새 대용량 신호와 한도 확대에는 이전 근거를 재사용하지 않습니다.

전체 완료 근거가 없는 조회에서 조건 누락, 긴 기간이나 큰 OFFSET 등 규모만 불확실한 경우에는 실행기가 한 번만 제한 COUNT를 수행합니다. 최대 50,001행까지만 세고 2초 실행 제한(연결 제한은 별도)을 적용하며 50,000행 이하면 바로 본 조회를 실행합니다. 초과하거나 규모 확인 시간이 지났을 때만 해당 범위를 묻습니다. 연결과 SQL 오류는 실패로 보고합니다. 진짜 조건 없는 조인, 알 수 없는 사용자 함수, 재귀나 한도 확대는 COUNT 결과만으로 허용하지 않습니다. 같은 범위의 작은 전체 완료 근거가 있으면 이 COUNT도 반복하지 않습니다.

`executed: false`는 결과가 아닙니다. 대기 메시지만 먼저 보내고 질문을 미루지 말고, `risks`와 조건 및 한도를 질문 도구에 함께 넣어 필요한 허락을 한 번 받습니다. 명확한 같은 범위의 기존 허락이 있으면 다시 묻지 않습니다. 승인 창을 여는 도구가 없을 때만 채팅으로 짧게 묻고 답변을 기다립니다.

```text
python -X utf8 -B "<스킬 절대경로>/scripts/query.py" run --plan <계획 ID> --confirm
```

`requiresLargeApproval`이 참이고 해당 위험을 허락받았을 때만 `--allow-large`를 추가합니다. `conditionsTruncated`만 참이면 로컬 `conditionReviewFile`로 전체 조건을 확인받으며 큰 조회 허락으로 확대하지 않습니다. 계획은 15분 뒤 만료되고 한 번만 실행합니다. SQL, 조건, 연결이나 한도가 달라지면 새 계획이 필요합니다.

기본 50,000행, 20MiB, 60초입니다. 확대 가능한 최대 범위는 1,000,000행, 512MiB, 1,800초이며 DB의 더 낮은 제한이 우선합니다.

기본 한도를 확대하려면 필요한 `--max-rows` 등을 지정해 새 계획을 준비합니다. 한도 안의 결과라도 서버 스캔 비용이 작다는 보장은 없습니다. 운영 전체 COUNT나 ANALYZE를 매번 추가하지 않습니다. 권한과 드라이버 제한은 사용자 허락으로 해제되지 않습니다.

## 결과 해석과 오류 처리

`deliveryVerification: verified`와 `verificationScope: csv-file-only`는 내보내기 중 원본 해시(기록된 경우), 논리 행과 열 수 및 저장 파일 크기를 실행기가 확인했다는 뜻입니다. `exportedRows`는 데이터 행 수, `outputBytes`는 헤더와 인코딩을 포함한 CSV 바이트 수입니다. 셀 내부 줄바꿈 때문에 물리적 줄 수가 더 클 수 있습니다. 이 영수증은 파일 전달 범위만 확인하며 DB의 `complete: false`를 성공으로 바꾸지 않습니다. 정상 저장 뒤 같은 파일을 다시 열고 줄 수를 세거나 `session verify`를 기록하지 않습니다. 사용자가 별도 검사를 요청했거나 파일을 후속 수정했다면 해당 범위만 새로 확인합니다.

| 응답 | 전달할 내용 |
|---|---|
| `status: complete`, `outcome: rows_returned` 또는 `empty` | 정상 완료와 행 수. 0건은 오류가 아닙니다. |
| `status: partial` | 일부 결과와 제한 이유. 전체 합계처럼 사용하지 않습니다. |
| `status: failed`, `outcome: error` | 오류 코드, 인증값을 가린 이유와 실패 단계. 0건으로 바꾸지 않습니다. |
| CSV 내보내기만 실패 | 기존 `resultId`로 재내보내기. SQL을 반복 실행하지 않습니다. |

`COUNT(*)` 결과 한 행의 값 0은 반환 행 수 0과 다릅니다. 오류를 피해 SQL, 날짜, 계정을 임의로 바꾸거나 재시도하지 않습니다. 비밀번호, 토큰, DSN과 전체 예외 추적은 출력하지 않습니다.

Oracle 접속 호출 자체가 실패하면 “HyDAP(Chakra)실행 여부 및 MyAccess권한 확인 부탁드립니다”를 안내합니다. SQL 오류, 결과 수신 실패, 조회 시간 초과나 드라이버 미설치에 이 문구를 붙이지 않습니다. 안내를 위해 추가 연결 시험을 하지 않습니다.

## 결과 파일과 재사용

새 조회는 항상 새로 실행합니다. 과거 결과를 쓰려면 조회 시각, 조건과 완전성을 알리고 허락받습니다. 사용자가 “방금 결과로 합계 내줘”처럼 지정한 결과의 후속 분석은 재조회하지 않습니다. 매번 캐시 재사용 여부를 묻지는 않습니다.

`oracle-query/outputs/`에는 전달할 CSV만 둡니다. 파일명은 쿼리명, 조회 시각과 결과 ID로 구분되며 일부 결과에는 `_일부`가 붙습니다. 원본 JSONL, metadata와 계획은 기존 개인 저장소에 있습니다. 경로는 응답의 `dataFile`과 `outputFile`을 사용합니다. 입력 명세가 필요할 때만 `oracle-query/.work/`를 쓰며 기존 `_work`나 사용자 파일을 임의 삭제하지 않습니다.

CSV는 수식처럼 보이는 문자열을 보호하며 원본 JSONL은 유지합니다. 식별자의 앞자리 0, 날짜와 정밀한 소수는 Python 후처리에서 자료형을 명시합니다. 행 전체를 대화로 출력하지 않습니다.

## 환경과 검증 범위

Python 3.11 이상과 requirements.txt의 의존성을 사용합니다. 기존 Python이나 다른 설정을 초기화하지 않습니다. 로컬 더미 검증은 실제 회사 계정, 사내망과 운영 DB/SDK 호환성을 보증하지 않습니다. `elapsedMs`는 처리 구간이며 LLM 생각 시간과 전체 업무 시간을 뜻하지 않습니다.

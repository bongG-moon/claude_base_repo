# Datalake 데이터 조회

요청한 데이터 조회만 수행합니다. 사내 `lakes.client.LakeHouse` SDK를 사용하는 로컬 Python 실행기이며 별도 하네스, MCP 등록이나 상시 후크가 필요하지 않습니다. 직접 API 연결로 자동 대체하지 않습니다.

## 사용 흐름

1. 현재 스킬의 `scripts/query.py`를 사용합니다. 조회 업무를 시작할 때 `start`를 한 번 실행해 인증 설정과 저장 쿼리, 24시간이 지난 결과의 정리 후보 요약을 확인합니다. 같은 업무의 반복 조회와 후속 분석마다 다시 실행하지 않습니다.
2. 정리 후보가 있을 때만 삭제 또는 보존을 한 번 묻습니다. 삭제는 준비된 정리 계획의 대상과 범위를 기준으로 실제 허락을 받은 뒤 `results cleanup --plan <계획 ID> --confirm`으로 수행합니다. 이미 사용자가 같은 범위의 삭제를 선택했다면 허락을 다시 묻지 않습니다. 후보가 없거나 보존을 선택하면 조회를 계속합니다. 인증정보와 저장 쿼리 원본은 정리하지 않습니다.
3. 저장된 사번, JWT, S3 Access Key와 S3 Secret Key를 그대로 재사용합니다. 인증정보가 없거나 필요한 값이 빠졌을 때만 `auth setup`으로 입력하며, 기존 인증이 있으면 최초 스킬 사용에서도 설정창을 열지 않습니다. 인증정보와 저장 쿼리 관리 화면은 요청할 때 `manage`로 엽니다. 인증값은 로컬 설정창이나 명시한 현재 작업 폴더의 `.env` 가져오기로만 받으며 상위 폴더를 탐색하지 않습니다. 키가 없으면 [My Key 발급 화면](https://lake.skhynix.com/myprofile/mykey)을 안내합니다. 설치와 가져오기 명령은 [사용 방법](references/usage.md)을 참고합니다.
4. 조회할 DB와 스키마, 테이블 정보는 입력 SQL의 `lake_catalog.스키마.테이블` 경로에서 정해집니다. Oracle처럼 DB를 등록하거나 DB 이름, 호스트, 포트, DSN을 따로 묻지 않습니다. SQL을 이름으로 저장할 때만 기간, 공정 등 바뀔 조건과 고정값을 구분합니다. 쿼리 등록은 조회 실행이 아닙니다. 새 테이블을 찾거나 컬럼과 파티션을 모를 때만 [테이블 탐색](references/discovery.md)을 읽고 저장 쿼리마다 탐색을 반복하지 않습니다.
5. 사용자가 쿼리와 필요한 조건을 지정해 조회를 요청했다면 기본 **50,000행**까지 `execute --id <번호> --params <조건 JSON> --confirm`으로 실행합니다. 본 조회의 파일 용량과 시간에는 기본 제한이 없으며 이를 위한 별도 확대 승인을 묻지 않습니다. 그 명시적 요청을 승인 근거로 삼고 같은 조건을 재확인하지 않습니다. 테이블 경로나 날짜 경계 등 의미가 불명확하거나 조건이 빠졌을 때만 묻습니다. 조건을 임의로 채우지 않습니다.
6. `execute`가 큰 조회의 승인이 필요하다고 멈추면 반환된 계획의 범위, 한도와 주의점을 짧게 보여줍니다. **사용자의 실제 허락 후** 그 계획을 `run --confirm --allow-large`로 실행합니다. 50,000행 초과뿐 아니라 넓은 기간과 위험한 SQL 형태도 이 절차를 따릅니다. SQL, 인증 계정, 조건이나 한도를 바꾸면 새 계획이 필요합니다.
7. `conditionsTruncated`가 참이면 `conditionReviewFile`의 전체 조건을 사용자가 로컬에서 확인한 뒤 실행합니다. 큰 조회가 아닌 경우 `run --confirm`이며 `--allow-large`는 큰 조회 승인도 필요할 때만 붙입니다. 사전 검토를 요청한 업무는 기존 `plan` 후 `run` 흐름을 사용합니다.
8. 결과의 `label`, 실제 경로, 저장 행 수와 완전성만 안내합니다. JSONL 전체, 원본 행이나 오류 원문을 대화에 넣지 않습니다. 후속 계산은 Python으로 저장 파일을 처리하고 필요한 집계만 반환합니다. 일부만 받은 결과를 전체 합계로 설명하지 않습니다.

## 알아둘 점

- 인증 설정의 별칭은 DB 이름이 아닙니다. 단일 인증정보를 재사용하며, 예전 설정이 여러 개면 사용할 계정만 한 번 확인합니다. 기존 쿼리를 수정할 때는 원래 인증정보를 유지하고 다른 계정이나 테이블로 조용히 대체하지 않습니다.
- 기존 SQL 파서로 단일 SELECT와 조건을 검사합니다. 환경변수로 쓰기 검사를 해제하지 않습니다. 조회 전용 계정도 필요하며 구문 검사만으로 모든 함수의 부수효과를 보증하지 않습니다.
- `start`와 관리 화면은 로컬 정보만 다룹니다. 실제 조회와 테이블 탐색은 사내 SDK를 호출합니다. SDK 내부의 연결, 클러스터 준비, 서버와 네트워크 자체 제한까지 해제되지는 않습니다.
- SDK의 `execute_pd(query=...)`는 결과를 pandas DataFrame으로 한 번에 받습니다. SQL의 행 한도를 적용해도 긴 컬럼이나 큰 결과는 파일 저장 전에 메모리를 많이 사용할 수 있습니다. 전체 COUNT와 ANALYZE는 자동 실행하지 않으며 결과 행 한도가 전체 스캔 부하를 보장하지 않습니다.
- 0건을 날짜 오류로 단정하지 않습니다. 사용자가 정한 기간과 조건을 보존하고 변경이 필요하면 이유를 설명해 허락을 받습니다. 다른 날짜로 자율 재조회하지 않습니다.
- `--confirm`, `--allow-large`는 실행 기록용 인자입니다. 인자 자체가 사용자의 의사를 인증하지 않으므로 허락을 꾸며 넣지 않습니다.
- 인증 실패나 시간 초과는 한 번 안내하고 멈춥니다. 다른 계정, 무한 재시도, 설정 탐색이나 더미 결과로 대신하지 않습니다.
- 기본 개인 저장소는 설치 폴더 밖입니다. 업데이트할 때 기존 인증정보, 저장 쿼리와 결과물을 덮어쓰지 않습니다.

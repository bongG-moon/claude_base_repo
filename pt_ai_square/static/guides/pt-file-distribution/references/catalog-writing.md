# 동료가 이해하고 찾을 수 있는 등록 글

도구를 처음 보는 동료에게 설명한다. 먼저 실제 자료에서 **받는 자료, 하는 일, 나오는 결과, 사용할 수 있는 환경**을 확인한다. 확인한 내용으로 이름과 소개를 쓴 뒤, 동료가 어떤 말로 찾을지도 살핀다. 이 기준은 글쓰기 안내이며 서버의 자동 개명이나 문체 검사 기능이 아니다.

## 이름과 소개

`name`에는 주된 동작 하나를 짧게 담는다. `업무 맥락 모아 보기`보다 `AI 업무 기록 정리`, `업무의 다음 단계를 더 쉽게`보다 `업무 메모로 주간 보고서 작성`처럼 무엇을 다루는지 알 수 있게 쓴다. 이름은 50자 이내다. 사용자가 확정한 제품명·고유명은 보존한다.

`desc`는 200자 이내의 1~2문장이다. 첫 문장에서 어떤 자료로 무엇을 만드는지 설명한다. 쓰임새가 이미 분명하면 한 문장으로 마쳐도 된다. 두 번째 문장이 필요하다면 언제 쓰는지 덧붙인다. `효율을 극대화합니다` 같은 효과를 붙이는 대신 실제 쓸 상황을 말한다. 근거 없는 시간 절약 수치나 자동화 범위를 추가하지 않는다.

`합니다`체로 쓰고, 제품을 소개하면서 `물론입니다` 같은 채팅 답변을 붙이지 않는다. 명사와 기술 용어를 나열하기보다 동사로 설명한다. 다만 독자가 도구를 고르는 데 필요한 제품명이나 제약까지 지우지는 않는다. 한 줄 소개를 만들려고 강제 줄바꿈이나 슬로건을 넣지 않는다. 화면 너비에 따른 자연스러운 줄바꿈은 그대로 둔다.

제목, 소개, 사용 안내, 동작 흐름과 추천 문장의 **나열에는 가운데점(`·`, `ㆍ`)이나 비슷한 점 기호를 쓰지 않는다.** 쉼표를 쓰거나 `와`, `과`, `및`으로 잇고, 나열이 길면 문장을 나눈다. 예를 들어 `글자·도형·표·차트를`은 `글자와 도형, 표, 차트를`로, `Claude·Codex의 기록`은 `Claude와 Codex의 기록`으로 쓴다. 코드, 식별자, 공식 고유명과 원문 인용은 임의로 치환하지 않는다. 이는 사용자 요청에 따른 AI SQUARE의 추가 기준이다. Humanizer KR 원문에 가운데점 전면 금지 규칙이 있다고 설명하지 않는다.

## 예시: 작업 기록을 모으는 도구

확인한 기능이 본인의 Claude와 Codex 업무 기록을 분류하고 저장된 스킬, 기억, 지식과 연결되는 업무의 처리 순서를 정리하는 것이라면 다음처럼 쓸 수 있다.

| 항목 | 작성 예시 |
|---|---|
| 이름 | AI 업무 기록 정리 |
| 짧은 소개 | Claude와 Codex에서 어떤 업무를 했는지 정리하고, 저장한 스킬과 참고 자료를 함께 볼 수 있는 보고서를 만듭니다. 다시 쓸 자료와 처리 과정을 찾아볼 때 사용합니다. |
| 관련 업무 태그 | 업무 기록, 작업 이력, 업무 현황, Claude, Codex |
| 사용 예시 | AI로 어떤 업무를 했고 다시 쓸 만한 자료는 무엇인지 정리해줘. |

실제 출력이 원문 목록이면 `요약합니다`라고 바꾸지 않는다. 도구가 기록을 계속 수집하지 않는다면 `자동으로 늘 최신 상태를 유지합니다`라고 쓰지 않는다. 설치·사용 안내에는 읽는 폴더와 기록 범위, HTML 결과를 여는 방법, 재집계 자료, 상시 수집이나 개인 평가에 사용하지 않는다는 원래 용도를 남긴다. 짧은 소개를 줄이는 과정에서 중요한 조건을 삭제하지 않는다.

이 예시를 다른 도구에 그대로 붙이지 않는다. 예를 들어 회의록 정리 도구가 아니라면 `회의록`, 모든 업무 앱을 읽지 않는다면 `전체 업무 기록`을 검색 태그에 넣지 않는다.

## 업무 표현을 검색 정보에 담기

이름을 모르는 동료가 요청할 법한 문장을 하나 떠올린다. 예를 들어 `이번 주 업무 메모를 보고서로 정리하고 싶어`라면 실제 지원되는 `업무 메모`, `주간 보고`, `보고서 작성`을 이름·소개·`workTags`에 자연스럽게 나누어 담는다. 사용 예시는 설치·사용 안내에 적되, 검색에 필요한 말을 안내에만 두지 않는다.

- 업무명뿐 아니라 다루는 자료와 동작도 넣는다. `보고서`, `엑셀`, `메일`처럼 대상이 드러나면 찾기 쉽다.
- 동료가 흔히 쓰는 말과 실제 제품명은 필요할 때 함께 쓴다. 예: `발표자료`와 `PPT`, `메일`과 `이메일`. 관련 없는 인기 검색어는 넣지 않는다.
- 태그는 최대 8개, 각 30자 이내다. 같은 뜻을 여러 개로 늘리거나 `업무`, `AI`, `효율` 같은 넓은 단어만 나열하지 않는다.
- 등록자 이름은 인증된 계정 정보로 검색되므로 태그에 사번이나 개인 정보를 넣지 않는다.
- `name`, `desc`, `workTags`를 사용한다. 새로운 검색 전용 필드를 배포 선언에 임의로 추가하지 않는다.

배포 Skill에서는 검색에 도움이 되는 이름과 설명, 태그를 준비하는 것으로 마친다. 플랫폼의 실제 검색은 MCP가 담당한다. MCP가 이 작성 기준을 참고해 결과를 설명할 때도 실제 기능과 필요한 조건을 짧게 알리고, 이름이 비슷하다는 이유만으로 기능이 맞다고 단정하거나 부서 선호와 설치 완료를 추측하지 않는다.

## 상세 안내와 동작 흐름

설치 안내는 사용할 때 필요한 순서로 쓴다. 준비할 프로그램·계정, 설치할 위치, 넣을 자료, 실행 방법, 결과 확인 방법을 실제 동작에 맞춰 설명한다. 개발자가 확인할 모듈명·파일 형식·경로 규칙은 필요한 단계에서만 설명한다. 필요한 권한·개인정보 처리 범위·지원하지 않는 환경은 누락하지 않는다.

`workflow.steps`도 사용자가 하는 일과 결과가 보이게 적는다. `데이터 인제스션` 대신 실제 동작인 `업무 메모 넣기`, `결과 정리` 대신 `보고서 초안 확인`처럼 쓴다. 원본에 없는 자동 분류·저장·검사를 만들어 넣지 않는다. 단계 수를 맞추려고 동작을 쪼개거나 합치지 않는다.

마지막에는 이름만 읽어도 동작이 보이는지, 소개를 읽고 언제 쓸지 알 수 있는지, 안내 없이 이해할 수 없는 기술 용어가 남았는지 확인한다. 문장을 자연스럽게 바꾸면서 사실과 조건이 달라지지 않았는지도 원본과 대조한다.

문체 참고: [Humanizer KR](https://github.com/hjongc/humanizer-kr). 사실을 보존하면서 추상적인 표현·과장·번역투를 줄이는 관점을 이 배포 안내에 적용했다. 외부 스킬 설치나 외부 서비스 호출은 필요하지 않다.

# 웹에서 읽는 배포 정보 v1

`assets/ai-square.example.json`을 실제 프로젝트에 맞게 채우고 ZIP 최상위에 `ai-square.json`으로 넣는다. 상위 폴더로 한 번 더 감싸지 않는다. 웹과 `scripts/prepare_package.py`가 같은 `package_contract.py` 규칙을 사용한다.

| 항목 | 규칙 |
|---|---|
| schemaVersion | 숫자 1 |
| packageId | 원본 패키지의 식별자. 3~80자, 영문 소문자 시작, 소문자·숫자·점·하이픈 |
| name / desc | 도구 이름 50자 / 한 줄 소개 200자 |
| platform | Claude / ChatGPT / 기타 |
| type | MCP/Tool / Skill / 플러그인/하네스 |
| entryPoint | 시작 파일의 ZIP 내부 상대 경로. Skill은 SKILL.md, Python MCP는 실제 시작 스크립트 등 |
| guideFile | UTF-8 설치 안내 파일 경로. 최대 40KB, 내용 1~10000자 |
| requiredFiles | 필요한 파일 경로 목록, 최대 100개. 시작 파일과 안내 파일도 항상 검사 |
| requirements | 사용자에게 알릴 의존성·권한·설치 조건, 최대 20개·각 200자. 설치 명령으로 실행하지 않음 |
| workTags | 선택, 최대 8개·각 30자 |
| environment / changes | 선택, 환경 200자 / 변경 설명 2000자 |
| workflow | 선택, `steps`만 가진 객체. 단계 1~8개, 각 `title` 필수 60자 / `description` 선택 240자 |

이름·소개·태그는 [등록 글 작성 기준](catalog-writing.md)에 따라 쓴다. `name`은 자료와 동작이 드러나는 짧은 이름, `desc`는 무엇을 하고 언제 쓰는지 설명하는 1~2문장이다. `workTags`에는 동료가 검색할 업무 표현을 실제 기능 범위에서 넣는다. 제품명이나 사용자가 확정한 이름을 임의로 바꾸지 않는다. 설치 조건은 `environment`, `requirements`, `guideFile` 내용에 구체적으로 남긴다. 서버가 문장을 자동으로 쉽게 바꾸거나 기술적 사실을 검사하는 것은 아니다.

경로는 `/` 구분자를 사용한다. 절대 경로, `..`, 빈 파일, 누락 파일, 중복 경로·중복 JSON 키, 알 수 없는 항목은 거절된다. guideFile 내용은 설치 안내 입력란으로 가져온다. 이름·설명·안내는 웹에서 검토하고 수정할 수 있다. 프로그램·유형은 ZIP과 일치해야 한다. 조직·업무 분야·담당자 표시명·권한은 웹 또는 게시 준비안에서 검토하며 패키지로 권한을 지정하지 않는다. 실제 등록자 사번은 인증된 계정으로 서버가 기록한다. 사번·부서코드·얼굴 사진·KEY는 배포 선언에 추가하지 않는다.

toolId·release·버전 확인 URL은 입력하지 않는다. 게시 후 웹에서 발급한 별도 배포 정보 JSON에 들어간다. 원본 ZIP은 서버에서 수정하지 않는다. JSON의 상대 URL은 사용자가 접속한 플랫폼 주소 기준이며 인증이 필요하다. 사용자가 실행 시 버전 확인 기능을 요청한 경우에만 배포할 도구의 실행 진입점과 인증 방법을 함께 설계한다. 일반 배포 파일에 버전 확인 코드나 KEY 입력 절차를 추가할 필요는 없다.

배포 정보가 없는 기존 ZIP·EXE·MSI·PS1·MD도 일반 등록을 유지한다. 웹에서 선언을 읽지 못하면 경고를 표시하고 수동 정보로 게시를 허용한다. 새 버전도 동일하다. 기존 도구를 선택해 업데이트하면 새 ZIP의 packageId가 달라도 등록할 수 있다. prepare_package.py는 제작 중 실수를 찾도록 잘못된 ZIP 선언을 계속 오류로 처리한다. ZIP 자체의 손상·안전하지 않은 경로는 웹에서도 차단한다. 선언은 코드의 실제 동작·호환성·보안 검증을 대신하지 않는다.

## 플랫폼 고정 ID와 원본 패키지 ID

- 숫자 `toolId`는 서버가 발급한 도구 번호다. 기존 도구의 업데이트 대상을 웹 또는 MCP에서 선택할 때 사용한다. 배포 Skill은 사용자가 이미 알려준 번호를 인계 정보로만 전달하고 ZIP에 넣지 않는다.
- API 최상위 `packageId`는 그 도구에서 처음 정상적으로 읽은 선언의 고정 ID다. 이후 새 ZIP의 선언이 달라져도 바뀌지 않는다. 선언 없이 등록한 도구는 첫 정상 선언을 게시할 때 정해진다.
- `sourcePackageId`는 해당 파일의 원본 선언 값이다. 버전별 `package.packageId`와 원본 ZIP도 이 값을 그대로 보존한다. `packageIdentityChanged`는 고정 ID와 원본 ID가 모두 있고 서로 다름을 알린다. 이 세 값은 플랫폼 응답용이며 ai-square.json에 새 필드로 추가하지 않는다.
- 같은 도구의 자료를 계속 만들 때 원본 packageId를 유지하면 후보 검색에 도움이 된다. 이미 다른 ID로 만들어진 새 파일도 기존 도구를 선택해 업데이트할 수 있으므로 ID만 맞추려고 압축을 다시 만들 필요는 없다. 새 원본 ID는 기존 도구의 자동 검색 별칭이 되지 않는다. 별도 신규 도구라면 신규 등록을 선택한다.
- 플랫폼의 고정 ID는 도구 선택을 돕는 값이며 전역 유일성을 보장하지 않는다. 같은 ID 후보가 여러 개이면 사용자가 숫자 도구 ID로 선택한다. 자료 경로의 로컬 연결 기록도 후보일 뿐 자동 게시 권한이 아니다.

ZIP의 `entryPoint`는 실제 존재하는 시작 파일을 가리켜야 한다. 자동 설치의 대상 경로는 별도 게시 정보 `installProfile.slug`, 실행 파일·인수는 `installProfile.entrypoint`와 명령 정보로 정한다. 원본 packageId를 수용하는 것과 설치 호환성은 별개다. 새 파일에 맞는 실행 경로와 기존 설치 위치·설정 보존 여부를 검토하고, 이 정보를 원본 packageId에서 추측하지 않는다.

단일 MD는 별도 ZIP 선언 없이 원본 파일로 배포한다. 터미널 명령어와 URL은 파일을 만들지 않고 웹에서 각각 등록한다. 연결 URL은 HTTP 또는 HTTPS의 호스트와 필요한 포트·경로를 사용하며 아이디·비밀번호를 주소에 넣지 않는다. 이 주소는 연결 안내이며 원격 MCP 자동 설정을 뜻하지 않는다. 명령어는 프로젝트용·내 계정 전역용을 나누어 입력하며 배포 버전별로 저장된다. 설치 범위와 실제 대상 경로는 사용자가 먼저 선택하도록 안내한다.

## 동작 흐름 표시

실제 코드·지침에서 확인한 업무 흐름을 순서대로 기록한다. 아래는 업무 메모를 주간 보고서로 정리하는 도구의 예시다. 서버는 이 텍스트를 도식으로 보여주며 코드를 실행하거나 문서를 LLM으로 분석하지 않는다. 근거가 없는 단계, 확인하지 않은 자동화·승인·보안 검사는 넣지 않는다. 의미가 불분명하면 작성자에게 확인하거나 workflow를 생략한다.

```json
{
  "workflow": {
    "steps": [
      {"title": "업무 메모 넣기", "description": "이번 주에 한 일을 적은 메모를 넣습니다."},
      {"title": "업무별로 나누기", "description": "메모를 업무 항목별로 나눠 보고서 초안을 만듭니다."},
      {"title": "보고서 확인하기", "description": "빠지거나 잘못 정리된 내용이 없는지 살펴봅니다."}
    ]
  }
}
```

제목·설명은 일반 텍스트다. HTML·Mermaid처럼 보이는 문자열도 코드로 해석하지 않는다. 실행 스크립트·URL 같은 별도 노드 속성은 받지 않는다. 복잡한 분기를 이 순서형 도식으로 왜곡하지 말고 핵심 단계만 적고 상세 조건은 설치·사용 안내에 설명한다. 흐름은 배포 버전별로 저장된다. 새 버전의 ZIP 선언이 흐름을 생략하면 이전 버전의 흐름을 재사용하지 않으며, 이전 버전으로 복구하면 그 버전의 흐름을 다시 표시한다. 승인형 도구는 조회 권한을 가진 사람만 흐름을 볼 수 있다.

단일 MD, URL, 명령어의 등록 자료를 준비할 때도 metadata JSON에 같은 `workflow` 구조를 넣을 수 있다. 실제 게시는 웹 또는 MCP에서 한다. 이 방식의 기존 도구 업데이트는 metadata에서 workflow를 생략하면 기존 흐름을 유지하고, 새 객체를 지정하면 교체하며, `"workflow": null`을 지정하면 제거한다. 흐름을 넣기 위해 MD를 ZIP으로 바꿀 필요가 없다. 일반 웹 수동 등록은 흐름이 없어도 정상적으로 게시된다.
